## 1. 진입점 — 프로필 아이콘

> **[정정, 2026-07-19]** 아래 §1 전체(프로필 아이콘 진입점)는
> `docs/superpowers/specs/2026-07-19-main-header-classification-and-settings-entry-design.md` §2로
> 대체되었다 — 최종 목업에 프로필 아이콘이 없고, 설정 진입점은 `CategoryToggleDropdown`(옷장/
> 코디/스타일일지 헤더 좌측 드롭다운) 메뉴 최하단으로 이동했다. 아래 원문은 이전 결정 기록으로
> 보존한다.

**결정: 프로필 아이콘은 상단 헤더의 `actions` 슬롯(우측)에 위치, 탭 시 `/settings`(`AppRoute.settingsTrash`)로 이동.**

- C4 `OverlayHeader`가 이미 `actions: List<Widget>` 슬롯을 지원하므로 별도 컴포넌트를 새로 만들지 않고 이 슬롯에 프로필 아이콘 버튼 하나를 추가한다 ((공통 규칙 문서의) 기능 재사용 원칙)
- 헤더 좌측은 기존 `[현재 컨텐츠 이름 ▾]` 드롭다운 트리거를 그대로 유지, 우측에 프로필 아이콘을 나란히 배치. 이 둘은 서로 다른 의도(드롭다운=카테고리 점프, 프로필 아이콘=Settings 진입)이므로 I1(제스처=의도 고정) 위반 아님 — 별도 탭 타겟이라 혼동 없음
- 02_IA&UserFlow.md: "Settings / Trash — Not included in the header dropdown" — 프로필 아이콘을 드롭다운 항목이 아닌 **별도의 헤더 액션**으로 두는 이번 결정과 정확히 부합
- **노출 범위(확정)**: 옷장/코디/스타일 일지 3개 **메인(루트) 화면**에만 노출. Detail/Add-Create 등 스택 깊은 화면에는 넣지 않음
    - 근거: 현재 옷장/코디/스타일일지 메인 라우트가 전부 placeholder라 실제 헤더 통합 전 단계이므로, 헤더 복잡도를 낮추기 위해 최소 범위(메인 루트만)로 잡는 실용적 스코프 판단 — 특정 원칙 문서보다 현재 구현 단계에 근거한 임시 결정. 카테고리 루트에서만 노출해도 프로필 아이콘 접근성은 충분히 확보됨(각 카테고리 드롭다운 선택 시 루트로 리셋되므로 최대 1탭이면 루트 복귀 가능)
    - 실제 헤더 인스턴스가 여러 화면에 실제로 붙기 전까지는 검증 불가한 논리적 판단이므로, 향후 헤더 셸 통합 작업 시점에 재검증 가능한 항목으로 남겨둠(전 화면 노출로 조정될 수 있음)
- **실제 통합은 이번 태스크 스코프 아님**: `lib/router/app_router.dart`의 옷장/코디/스타일 일지 메인 라우트가 전부 `_placeholder()`라 아직 실제 `OverlayHeader` 인스턴스가 어느 화면에도 붙어 있지 않다. 이 문서는 프로필 아이콘의 **논리적 위치/탭 동작만 명세**하며, 각 메인 화면을 placeholder에서 실제 헤더 셸로 교체하는 작업(Layer=UI/Screen, Stage=Implementation)은 별도 태스크로 넘긴다
- 아이콘 터치 영역: A1(44×44pt 최소) + A10(시각적 아이콘 크기와 무관하게 히트 영역 확보)

## 2. 화면 구성 — 리스트 로우 4개 (확정, 2026-07-27 — 아래 로우 2/3은 이번 갱신으로 신설, 로우 1/4은 2026-07-09 원 스펙 그대로)

### 로우 1 — 알림 on/off (토글)

- 리스트-로우 + 우측 `Switch`. 라벨 "알림"
- 탭(로우 전체 또는 스위치) 즉시 상태 전환 — 별도 확인 없음
    - 근거: P1(유틸리티 경로=속도 우선, 불필요한 확인 마찰 없음), P3(액션은 즉시 반영·즉시 가시화가 기본값)이고, 알림 on/off는 파괴적이지도 되돌릴 수 없지도 않으므로 확인 절차 대상(I6)에 해당하지 않음
- 상태 저장 대상(로컬/서버, 알림 권한 연동 등)은 데이터/아키텍처 결정 사항으로 이 문서 범위 밖. UI는 스위치 상태를 즉시 반영하고 유지하는 동작만 정의
- 접근성: A1/A10(스위치 히트 영역 44×44 이상), A13(스위치 on/off 상태를 스크린리더에 텍스트로 노출 — 시각적 스위치 위치만으로 상태 전달 금지)

### 로우 2 — 다크 모드 (토글, 신설 2026-07-27)

- 리스트-로우 + 우측 `Switch`. 라벨 "다크 모드". "일반" 섹션에서 알림 바로 아래 배치
- 탭 즉시 상태 전환 — 근거는 로우 1(알림)과 동일(I6 확인 절차 대상 아님, P1/P3)
- **UI 스펙 범위**: 이 로우는 토글 UI 동작만 정의한다. 실제 앱 전체 테마 전환(`ThemeMode` 적용)은 Logic/Feature 레이어 구현 사항으로 범위 밖 — 현재 `main.dart`가 `themeMode: ThemeMode.light`로 고정돼 있어 토글해도 실제 테마가 바뀌지 않는 상태이며, 이 실동작 배선은 별도 백로그 태스크로 관리(`BACKLOG.md` 참고)
- 접근성: 로우 1과 동일(A1/A10/A13)

### 로우 3 — 휴지통 진입 (체브론, 신설 2026-07-27)

## 3. 로그아웃 confirm 처리 — Toast+Undo 채택 (C11 미사용)

**결정: 로그아웃 탭 시 블로킹 confirm 모달(C11 `DestructiveConfirmModal`)을 사용하지 않는다. 대신 즉시 실행 + Toast+Undo(C7 `UndoableActionToast`) 패턴을 재사용한다.**

판단 근거:

- I6(Interaction Principles): "confirm 모달은 (a) 비가역 액션 또는 (b) 가역이지만 하위 파급이 비가역인 액션에만 허용. 그 외 액션엔 confirm 스텝을 넣지 않는다." 로그아웃은 재로그인으로 완전히 되돌릴 수 있고, 오프라인 정책(공통 규칙 문서: "기본은 로컬 저장, 로그인 시 클라우드 저장", "비로그인·오프라인 상태에서도 이어서 사용 가능")에 따라 로그아웃해도 로컬 데이터가 삭제되거나 접근 불가능해지지 않는다 — 즉 (a)에도 (b)에도 해당하지 않음
- I6/P1 AI Constraints에 "reversible action에 confirm 다이얼로그를 '안전해 보이려고' 추가하지 말 것"이 **명시적으로, 두 문서(UX Principles §6, Interaction Principles §4)에 중복 기재**되어 있음. "로그아웃은 보통 확인창을 띄운다"는 일반적 관행이 있으나, 이 프로젝트 원칙 문서는 정확히 이 케이스(가역인데 관성적으로 confirm을 붙이는 것)를 금지 대상으로 지목하고 있으므로 관행보다 문서 원칙을 우선함
- C11은 Component Strategy에서 "I6(비가역 액션 전용) 구현체"로 명시적으로 스코프가 좁혀져 있음. 로그아웃에 C11을 재사용하면 컴포넌트가 실제 구현하는 규칙(I6, 비가역)과 화면상 의미가 어긋나 사용자에게 실제보다 더 위험한 액션으로 오인시킬 수 있음 — "재사용 원칙"은 규칙이 실제로 적용되는 경우에만 해당하므로, 여기서는 재사용이 아니라 오용에 해당
- I5/C7 선례: "코디 삭제 → 즉시 휴지통 이동 + Toast의 단일 실행취소, confirm 다이얼로그 없음"과 구조적으로 동일한 케이스(가역 상태 전환)이므로 동일 패턴 적용이 일관성 있음
- **C7 스코프를 레코드 단위에서 계정 단위로 확장하는 근거**: `06_Component Strategy.md`의 C7 "state store"는 삭제-항목 리스트라는 특정 저장소를 가리키는 것이지, 위젯(토스트 UI + undo 콜백 타이머) 자체의 적용 범위를 레코드로 제한하는 것이 아니다. 로그아웃은 기존 삭제-항목 스토어와 공유하지 않는 독립된 세션 상태를 backing store로 사용하므로 "C7/C8 간 상태 스토어 공유 금지" 제약과 무관하다. 따라서 C7의 UI 패턴(즉시 실행+Toast+Undo)을 레코드 단위에서 계정 단위 가역 상태 전환으로 일반화해 재사용하는 것은 "새 컴포넌트를 만들지 말고 기존 인벤토리를 재사용하라"는 원칙에 부합하는 확장이다 — 단, 로그아웃용 세션 상태는 C7의 기존 삭제-항목 상태 스토어와 별개의 독립 스토어여야 한다

동작 정의:

- 로그아웃 탭 → 즉시 로그아웃 상태로 UI 전환 (Settings 화면 자체는 유지, 별도 화면 전환 없음) → 화면 하단 Toast "로그아웃되었습니다 [실행취소]" 노출, 시간 제한 창 내 실행취소 가능
- 실행취소 시 로그인 상태 복원, 창 만료 시 로그아웃 확정
- **00_페이지 타입 정의의 Utility형 규정("파괴적 액션은 스와이프 또는 별도 확인 절차로 한 단계 더 진입")과의 관계**: 이 규정은 Stage 3(Layout/Page Type) 수준의 일반 지침이고, I6(Stage 2, Interaction Principles)이 confirm 모달 사용 조건을 비가역 액션으로 더 구체적으로 좁혀 정의한다. 로그아웃처럼 다중 레코드 목록이 아닌 단일 계정-레벨 액션에는 "스와이프" 옵션도 의미가 없고(스와이프는 리스트의 개별 레코드 삭제에 적합한 단축 액션), Toast+Undo가 곧 "별도 확인 절차"의 대체재 역할(실행 후 되돌릴 여지 제공)을 한다고 해석 — 두 문서가 문면상 충돌하는 지점이었으나, **Design Review에서 이 해석이 원문 근거(I6/P1 AI Constraints, C11 스코프 명시)로 확인·승인됨(2026-07-09)**
- 실제 세션 무효화(auth 토큰 폐기 등) 로직은 다루지 않음 — 아래 4번 참고

## 5. 세션/로그인 시스템 부재

- 코드베이스에 실제 로그인/세션 시스템이 아직 없음(mock 데이터 단계). 이 문서가 정의하는 "로그아웃"은 **UI 셸 동작(즉시 로그아웃 상태 전환 + Toast+Undo)까지만**이며, 실제 로그아웃 대상이 되는 세션/인증 토큰이 없다
- 실제 인증 연동, 세션 무효화, 로그인 화면/플로우 자체의 존재 여부(로그인 진입점이 어디 있는지 등)는 이 결정 문서의 범위 밖이며 별도 Data/Architecture 또는 Logic/Feature 레이어 결정 사항으로 남긴다

## 6. 접근성 요약

- A1/A10: 알림/다크모드 스위치, 휴지통 체브론 히트 영역 44×44pt 이상 (시각 크기와 무관). **[갱신, 2026-07-27]** 기존 "프로필 아이콘" 항목은 §1의 2026-07-19 정정(헤더 아이콘 자체가 폐기, 설정 진입점이 드롭다운 메뉴로 이동)으로 무관해져 제거
- A2: 로그아웃 로우는 색상(Error) + 아이콘 + 텍스트 병기, 색상 단독으로 destructive 의미 전달하지 않음
- A3: 다크모드 포함 대비비 준수 (Error 롤 다크 변형 `#D98A8E` 사용)
- A13: 알림/다크모드 스위치 on/off 상태를 스크린리더에 텍스트로 노출
- A13: 로그아웃 Toast 메시지도 상태 변경 알림(WCAG 4.1.3 Status Messages)에 준해 스크린리더에 전달되어야 함
