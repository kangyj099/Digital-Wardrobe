# Figma 슬라이드 제작 프롬프트

---

## 1. Context & Audience

이 발표자료는 **IT 기업 입사 지원 서류에 첨부할 포트폴리오**입니다. 인사담당자와 기술 면접관, 실무진에게 순차적으로 전달됩니다.

## 2. Structure Constraint

- 1페이지당 1개의 핵심 메시지만 담아주세요. 부가 정보는 핵심 메시지를 보조하는 수준으로만 배치합니다.
- 총 8슬라이드 구성이며, 아래 슬라이드별 내용은 이미 확정된 카피 기준입니다. 슬라이드 4~6에는 프로젝트의 실제 워크플로우 문서(`.claude/agents/`, `Workflow_Project.md` 등)에서 가져온 상세 설계 내용이 포함되어 있는데, 이는 기술적 기여도를 보여주기 위한 의도적 배치이니 임의로 축약하지 말고 아래 문구를 최대한 살려주세요.

## 3. Content Grounding

- **제공되지 않은 성과나 수치, 경험은 절대 추가하지 말 것.** 프로젝트가 아직 미완료 상태라 일부 정량 수치(개발기간, 구현 화면 수, PR 건수 등)는 확정할 수 없습니다.
- 이런 항목은 **플레이스홀더로 명확히 표시**해주세요. 형식: `[PLACEHOLDER: 항목명]`
  - 시각적으로도 구분되게 처리해주세요 (예: 점선 테두리 박스 + 옅은 회색 텍스트, 또는 "추후 업데이트" 뱃지). 나중에 실제 값을 넣을 때 한눈에 찾을 수 있어야 합니다.
  - 절대 임의의 숫자나 예시 수치를 만들어 넣지 마세요.

### Slide 3 — 앱다운 UX 철학
- 레이아웃: `Tiled_Text_With_Icons` (3열 타일)
- 핵심 메시지: 웹을 감싼 앱이 아닌 '진짜 앱'을 만들기 위한 디자인/기능 선택
- 3개 타일:

  2. **유기적인 화면-데이터 연결** — 단순 기능 나열식이 아닌, 화면과 데이터 간 연결 구조에 집중
  3. **모바일 네이티브 제스처 지원** — 제스처 문법에 익숙한 유저에게는 빠른 사용성을, 익숙하지 않은 유저에게는 가시적 버튼과 비주얼 암시로 불편함 없는 경험 제공

### Slide 4 — Claude Code 기반 AI 파이프라인 (멀티 에이전트 하네스)
- 레이아웃: `Tiled_Text_With_Icons` (3열 타일)
- 핵심 메시지: **역할 분리형 멀티 에이전트 하네스 엔지니어링**으로 실제 SDLC를 구현
- 왜 이 방식을 택했는가 (2개로 압축):
  - 혼자서 여러 역할(기획/디자인/개발/검증)을 겸해야 하는 상황에서, 역할을 명확히 분리하면 AI 결과물의 품질이 높아진다는 원칙(`Workflow_Project.md §1.1`)을 실제로 검증해보고 싶었음
  - AI를 단순 코드 생성기가 아니라 협업 도구로 어디까지 활용할 수 있는지 확인하고 싶었음
- 구조 (도표로 표현):
  - `.claude/agents/`에 PM / Worker / Review / Tester / Audit / Integrator 역할이 분리되어 있고, 루트 세션이 PM 역할을 맡아 실제 구현·검증은 서브에이전트에게 위임
  - Task 크기(S/M/L/XL)별로 다른 파이프라인 적용:
    - S: Worker → Complete
    - M: Worker → Review → Tester → Complete (실패 시 재검증 루프)
    - L/XL: 여기에 Integrator(또는 사람) + Feature Audit 추가
  - 거시적으로는 기획-디자인-프론트엔드-백엔드 Waterfall 순서, 각 파트 내부에서는 서브에이전트 핸드오프를 주고받는 Agile 방식 — 전체 제어는 PM(사람)이 담당

### Slide 5 — Git-flow & 세션 컨텍스트 관리
- 레이아웃: `Diagram_Full_Width`
- 핵심 메시지: 브랜치 전략과 문서 체계로 "AI 세션은 기억하지 못한다"는 전제를 방어
- 다이어그램 중심, 텍스트는 캡션 수준:
  - Git-flow: main(release) — dev(development) — feature/*(작업 브랜치). AI는 feature에서 작업 후 dev로 PR 요청, **PR 컨펌은 항상 사람이 진행**
  - 문서 기반 Source of Truth: `docs/reference/`(기획·디자인 레퍼런스), `docs/history/`(Decision·TechnicalDebt 누적 기록), `docs/work/BACKLOG.md`(진행 상태 스냅샷) — "AI 세션은 프로젝트의 저장소가 아니다"라는 원칙(`§1.3`)을 문서 구조로 실현
  - 사람의 검수: PR을 항상 직접 읽고 확인. 중요한 결정이나 방향성은 사람이 정하고, 문제 발생 시 파이프라인 자체를 검토·수정

### Slide 6 — 품질 보증 체계
- 레이아웃: `Two_Column_Tiled_Text`
- 핵심 메시지: 정책 계층 구조 + 3단계 검수로 AI의 일관성 이탈을 방지
- 좌측 (정책 상속 구조):
  - 상위 정책을 하위 정책이 계승하고 필요한 부분만 구체화(override)
  - `project → design / development → db`
  - Layer(UI·Screen / Logic·Feature / Data·Architecture) × Stage(Decision / Implementation)로 Task를 태깅해, 필요한 자료만 골라 Worker/Review에게 전달(Task Manifest) — 전체 컨텍스트를 매번 넘기지 않아 토큰과 노이즈를 줄이는 설계
- 우측 (검수 프로세스):
  - Task 규모에 따라 Review → Test → Audit 3단계를 거쳐 AI 스스로 일관성/목적 부합 여부를 검수하게 함
  - 사람의 검수: 충분한 시간을 들여 AI 산출물을 검토. 평소 익숙하지 않던 분야(기획/디자인/프론트엔드)도 단계마다 개념을 학습하며 접근
  - 지향점: "AI틱하지 않은" 체계적이고 단단한 산출물. 어설픈 MVP는 만들 수 있어도 유지보수·디벨롭이 안 되는 상황을 경계함

### Slide 7 — 회고 및 인사이트

## 5. Style & Visual Guidelines

디자인 토큰은 첨부된 `docs/design-tokens-for-figma-handoff.md` 파일을 참고해주세요. 이 파일 안에 실제 앱 스크린샷 이미지 링크도 포함되어 있으니, 색상/블러/라운드 값뿐 아니라 시각적 톤앤매너도 이 파일을 기준으로 맞춰주세요.

핵심만 다시 요약하면:
- 컬러: bg `#F7F6F3`, primary `#394550`, accent `#C5D3C7`, 배경 그라디언트 `#EEEAE1→#E6E0D3`
- 글래스: `background rgba(247,246,243,0.38)`, `border rgba(247,246,243,0.20)`, `backdrop-filter: blur(3px) saturate(180%)`
- Radius: pill 19px / 카드 16px / 아이콘버튼 8px / 원형버튼 50%
- Shadow: `0 2px 10px rgba(43,45,48,0.06), inset 0 1px 0 rgba(255,255,255,0.16)`
- 폰트: `'Pretendard', 'Noto Sans KR', sans-serif`, weight 600~800 위주

프로스티드 글래스 + 플로팅 버튼 모티프를 슬라이드 자체의 UI 요소(예: 페이지 하단 파트 인디케이터)에도 일관되게 적용해주세요.

## 6. Figma 기술 스펙

- **프레임 크기**: A4 기준
- **방향(가로/세로)**: 정해진 방향 없음. 슬라이드마다 내용을 가장 잘 표현할 수 있는 방향으로 자유롭게 선택하되, **덱 전체는 하나의 방향으로 통일**해주세요.
- **레이아웃 컴포넌트**: `Title_Slide`, `Image_Right_Text_Left`, `Tiled_Text_With_Icons`, `Diagram_Full_Width`, `Two_Column_Tiled_Text`, `Q&A`는 기존 Figma 파일에 존재하는 컴포넌트가 아니라 **레이아웃 구조를 설명하는 개념적 이름**입니다. 각 슬라이드마다 auto-layout으로 새로 구성해주세요.
- **텍스트 오버플로우 처리 순서** (이 순서를 반드시 지켜주세요):
  1. 지정된 레이아웃 영역을 벗어나면 먼저 자동 줄바꿈 시도
  2. 줄바꿈으로도 세로로 넘칠 경우, 텍스트를 더 컴팩트하게 축약 시도(같은 의미를 유지하며 문장을 짧게)
  3. 그래도 넘칠 경우 폰트 크기를 줄여서 맞춤
- **작업 완료 후**: 전체 슬라이드 작업이 끝나면, 어떤 슬라이드에서 텍스트를 축약했는지·폰트를 줄였는지·플레이스홀더가 몇 개나 남아있는지 요약해서 알려주세요.

## 7. Review & Testing

초안 작성 후 아래 4가지를 검토한 뒤 반영해주세요:
1. 기술적 기여도가 명확히 드러나는지 (특히 슬라이드 4의 하네스 구조, 슬라이드 6의 정책 계층 구조)
2. 제공된 정량적 수치가 잘 강조되었는지
3. 가독성이 좋은지
4. 플레이스홀더 항목이 시각적으로 명확히 구분되어, 나중에 실제 값으로 쉽게 교체할 수 있는 상태인지
