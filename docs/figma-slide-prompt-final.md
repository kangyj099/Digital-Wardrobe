## 3. Content Grounding

- **제공되지 않은 성과나 수치, 경험은 절대 추가하지 말 것.** 프로젝트가 아직 미완료 상태라 일부 정량 수치(개발기간, 구현 화면 수, PR 건수 등)는 확정할 수 없습니다.
- 이런 항목은 **플레이스홀더로 명확히 표시**해주세요. 형식: `[PLACEHOLDER: 항목명]`

- 앱 관련 이미지를 배치하는 게 적합해 보이는 슬라이드가 있으나 앱이 아직 미완료라 적절한 화면 스크린샷이 없는 경우, 해당 위치를 이미지 플레이스홀더로 지정하고 추후 어떤 이미지를 넣으면 좋을지 메모를 함께 남겨주세요.

### Slide 3 — 앱다운 UX 철학 Native App UX Principles

#### 핵심 메시지

> **웹을 감싼 앱이 아니라, 모바일 환경 자체를 기준으로 설계했다.**
> 

이 페이지는 기능 목록을 보여주는 페이지가 아니다.

**"왜 이런 UI/인터랙션을 선택했는가"**를 보여주는 페이지다.

---

#### 3-1. Lightweight UI

##### 화면 여백을 지키는 가벼운 UI

작은 모바일 화면에서 콘텐츠 영역을 최대한 확보하기 위해:

- 불투명한 고정 바를 최소화
- 반투명 Glass UI 활용
- 플로팅 버튼 사용

을 선택했다.

핵심:

> **UI가 콘텐츠를 차지하지 않고 콘텐츠 위에 가볍게 존재하도록 설계**
> 

---

#### 3-2. Connected Interaction

##### 탭을 통한 유기적인 연결

보이는 값과 이미지가 곧 다음 정보로 연결된다.

사용자가 궁금한 것을 발견하면:

**탭 → 정보 확인 → 관련 화면 이동**

으로 이어진다.

핵심 원칙:

> **화면은 읽고 끝나는 것이 아니라, 항상 다음 행동으로 연결될 수 있어야 한다.**
> 

---

#### 3-3. Native Gesture

##### 모바일 네이티브 제스처 지원

모바일 사용자가 익숙한 제스처 문법을 적극적으로 활용한다.

제스처에 익숙한 사용자에게는:

> **빠른 사용성**
> 

을 제공하고,

제스처에 익숙하지 않은 사용자에게는:

> **가시적인 버튼 + 시각적 암시**
> 

를 함께 제공한다.

즉,

> **제스처 중심이지만 제스처를 강요하지 않는다.**
> 

---

#### 시각적 구성

3개의 원칙을 단순한 동일 크기의 **카드 3개**로 표현하는 것에 한정하지 않는다.

각 원칙의 특징을 보여줄 수 있도록:

- 실제 앱 UI 일부
- 제스처 방향
- Floating UI
- 연결 관계
- 인터랙션 흐름

등을 **시각적 자료로 크게 활용**한다.

텍스트는 설명문이 아니라 **시각 자료를 이해시키는 캡션**에 가깝게 사용한다.

### Slide 4 — Claude Code 기반 AI Pipeline

**Multi-Agent Harness**

#### 핵심 메시지

> **폭포수 형태의 SDLC 안에 반복적인 에이전트 작업 루프를 넣고, 작업 크기에 따라 검수 공정을 확장했다.**
> 

이 페이지는 정보를 예쁘게 정리하는 페이지가 아니다.

**전체 파이프라인의 구조를 하나의 강한 시각적 composition으로 보여주는 것이 목적이다.**

도표가 이 페이지의 **주인공**이며, 텍스트는 도표를 설명하는 보조 요소다.

---

#### 4-1. SDLC 전체 흐름

먼저 전체 개발 과정은 직선적인 흐름으로 보여준다.

**기획 → 개발 → 테스트 → 릴리즈**

이것이 전체 프로젝트의 큰 흐름이다.

---

#### 4-2. Agent Loop

위 SDLC 중 실제 작업이 수행되는 부분을 확대해서:

**Worker → Review → Tester → Audit**

의 반복적인 작업 루프로 표현한다.

단순한 네모 박스 나열이 아니라 **순환 구조**가 명확하게 보여야 한다.

실패하거나 수정이 필요한 경우 다시 이전 단계로 돌아가는 **loop-back** 관계를 시각적으로 표현한다.

---

#### 4-3. Task Size별 Pipeline

작업 크기에 따라 참여하는 공정이 달라진다.

##### S

**Worker → Complete**

##### M

**Worker → Review → Tester → Complete**

실패 시:

**Review ↔ Tester**

재순환.

##### L / XL

**Worker → Review → Tester → Audit → Integrator(사람) → Complete**

작업이 커질수록 검수 단계가 추가된다.

---

#### 4-4. 작업 크기 시각화

작업 크기를:

**S → M → L → XL**

순으로 시각적으로 무겁게 표현한다.

도표에서:

- S: 가장 가벼움
- M: 중간
- L: 무거움
- XL: 가장 무거움

이 차이가 **도형의 크기 / 두께 / 밀도** 등으로 직관적으로 드러나야 한다.

색상은 Primary `#394550`을 기반으로 사용한다.

작업이 커질수록 파이프라인도 시각적으로 무거워지는 인상을 준다.

단순히 동일한 크기의 네모 박스를 반복해서 배치하지 않는다.

---

#### 4-5. Agent Ownership

도표 주변의 짧은 캡션으로:

> **각 작업은 PM이 스폰한 개별 서브에이전트가 담당한다.**
> 

구조:

**PM (Root Session)**

↓

**Worker / Review / Tester / Audit**

---

#### 4-6. Waterfall + Agile

도표 하단에 짧은 캡션:

> **기획·디자인·프론트엔드·백엔드는 Waterfall, 서브에이전트 핸드오프는 Agile — 전체 제어는 PM**
> 

---

#### 4-7. Why

도표 한쪽에 짧은 캡션 수준으로:

**역할 분리**

→ AI 결과물 품질 향상

**AI를 협업 도구로 활용**

→ 실제 개발 과정에서 AI 오케스트레이션 가능성 검증

`Workflow_Project.md §1.1`의 근거를 활용한다.

---

#### 시각적 우선순위

이 페이지에서는:

**도표 >>> 텍스트**

다이어그램이 페이지의 상당 부분을 차지해야 한다.

텍스트를 여러 개의 카드로 감싸서 정보를 정리하는 방식보다,

**큰 도표 + 짧은 캡션 + 포인트 라벨**

구조를 우선한다.

### Slide 5 — Git-flow & Session Context Management

#### 핵심 메시지

> **AI 세션의 기억에 의존하지 않고, Git과 문서를 Source of Truth로 사용한다.**
> 

이 페이지는 두 가지 독립된 개념을 보여주지만, 둘 모두 **"AI 세션 밖에 프로젝트의 기억을 남긴다"**는 하나의 원칙으로 연결된다.

---

#### 5-1. Git-flow

Git 브랜치 구조를 시각적으로 보여준다.

**main**

Release

↓

**dev**

Development

↓

**feature/***

Individual Task

작업 흐름:

**feature → dev → main**

AI는 feature branch에서 작업한다.

작업 완료 후:

**PR 요청 → 사람 확인 → Merge**

PR 컨펌은 항상 사람이 진행한다.

핵심 원칙:

> **AI가 코드를 작성할 수는 있지만, 최종 통합 결정은 사람이 한다.**
> 

---

#### 5-2. Source of Truth

프로젝트의 기억을 문서와 Git에 남긴다.

##### `docs/reference/`

기획 / 디자인 레퍼런스

##### `docs/history/`

Decision / TechnicalDebt 누적 기록

##### `docs/work/BACKLOG.md`

현재 진행 상태 Snapshot

이 구조를 통해:

> **AI 세션은 프로젝트의 저장소가 아니다.**
> 

라는 원칙을 구현한다.

---

#### 5-3. Human Review

Git-flow와 문서 구조의 최종 통제점은 사람이다.

사람은:

- PR을 직접 읽고 확인
- 중요한 방향과 의사결정 직접 결정
- 문제가 반복되면 개별 코드뿐 아니라 **파이프라인 자체를 검토**

한다.

즉,

**AI가 작업 → 문서/Git에 기록 → 사람이 검수 → 다음 작업**

이라는 구조다.

---

### 5-4. Git + Documentation Relationship

이 페이지의 핵심은 Git-flow와 문서 구조를 **각각 별도의 카드로 보여주는 것**이 아니다.

다음 관계가 시각적으로 드러나야 한다.

**AI 작업**

↓

**Git / Documentation**

↓

**Human Review**

↓

**Next Task**

즉,

> **AI의 작업 기억을 세션이 아니라 프로젝트 구조에 저장한다.**
> 

---

#### 시각적 우선순위

이 페이지는 **Git branch diagram + Documentation structure**가 주된 시각 요소다.

## 5. Style & Visual Guidelines
### 디자인 원칙
#### 1. 웹 UI처럼 만들지 않는다

다음과 같은 표현을 과도하게 사용하지 않는다.

- 카드
- 타일
- 둥근 사각형
- subtle shadow
- glassmorphism
- 작은 아이콘 카드
- dashboard grid
- SaaS landing page 스타일
- 모든 콘텐츠를 동일한 박스 안에 넣는 구성

**도형을 사용하는 것 자체는 문제가 아니다.**

다만 도형은 콘텐츠를 감싸기 위한 기본 컨테이너가 아니라, **정보의 구조·방향·강조·관계를 표현하기 위한 시각 언어**로 사용한다.

---

#### 2. 슬라이드의 공간을 적극적으로 사용한다

화면 가장자리의 여백은 비교적 타이트하게 사용한다.

대신 콘텐츠 그룹 사이의 여백을 무작정 크게 벌려서 "여유로운 디자인"을 만들지 않는다.

원하는 밀도는:

> **바깥 여백은 타이트 / 핵심 콘텐츠는 크게 / 내부 관계는 촘촘하게**
> 

이다.

슬라이드가

> "내용이 적어서 비어 있다"
> 

는 인상을 주지 않도록 한다.

---

#### 3. 중요한 도표는 작게 만들지 않는다

도표가 해당 페이지의 핵심 정보라면 **페이지의 상당 부분을 차지하도록 크게 제작한다.**

특히 Slide 4와 Slide 5는 도표가 장식이 아니라 **페이지의 주 콘텐츠**다.

작은 도표 + 큰 설명문 형태로 만들지 않는다.

---

#### 4. 텍스트는 "내용을 채우기 위한 요소"가 아니다

본문을 길게 배치하여 빈 공간을 채우지 않는다.

가능하면:

**큰 제목 → 핵심 키워드 → 짧은 설명 → 큰 시각화**

구조로 만든다.

텍스트는 도표를 설명하거나 강조하는 **편집적 캡션**처럼 사용할 수 있다.

---

#### 5. 타이포그래피는 충분히 크게

발표자료이므로 작은 글씨를 사용하지 않는다.

특히:

- Slide Title
- 핵심 키워드
- 다이어그램 라벨
- 숫자
- 주요 지표

는 멀리서도 읽힐 수 있는 크기로 제작한다.

"정보가 많으니 글자를 작게 줄이는 것"은 해결책으로 사용하지 않는다.

### 슬라이드 8장 전체의 시각적 리듬

모든 슬라이드를 동일한 템플릿으로 만들지 않는다.

특히 다음과 같은 반복을 피한다.

> 제목 → 설명 → 카드 3개 → 카드 3개 → 하단 캡션
> 

대신 슬라이드의 정보 성격에 따라 **시각적 중심을 바꾼다.**

| Slide | 시각적 중심 |

| 1 | 앱 이미지 / Typography |
| 2 | Needs → Persona → MVP |
| 3 | UX 원칙 + 모바일 UI |
| 4 | **대형 AI Pipeline Diagram** |

특히 **4, 5, 6은 정보 시각화 중심의 페이지**로 만든다.

## 6. Figma 기술 스펙

- **프레임 크기**: 기본 A4 기준, 16:9도 가능.
- **방향(가로/세로)**: 정해진 방향 없음. 슬라이드마다 내용을 가장 잘 표현할 수 있는 방향으로 자유롭게 선택하되, **덱 전체는 하나의 방향으로 통일**해주세요.
- **레이아웃 컴포넌트**: `Title_Slide`, `Image_Right_Text_Left`, `Tiled_Text_With_Icons`, `Diagram_Full_Width`, `Two_Column_Tiled_Text`, `Q&A`는 기존 Figma 파일에 존재하는 컴포넌트가 아니라 **레이아웃 구조를 설명하는 개념적 이름**입니다. 각 슬라이드마다 auto-layout으로 새로 구성해주세요.
- **텍스트 오버플로우 처리 순서** (이 순서를 반드시 지켜주세요):
  1. 지정된 레이아웃 영역을 벗어나면 먼저 자동 줄바꿈 시도
  2. 줄바꿈으로도 세로로 넘칠 경우, 텍스트를 더 컴팩트하게 축약 시도(같은 의미를 유지하며 문장을 짧게)
  3. 그래도 넘칠 경우 폰트 크기를 줄여서 맞춤
- **작업 완료 후**: 전체 슬라이드 작업이 끝나면, 어떤 슬라이드에서 텍스트를 축약했는지·폰트를 줄였는지·플레이스홀더가 몇 개나 남아있는지 요약해서 알려주세요.
